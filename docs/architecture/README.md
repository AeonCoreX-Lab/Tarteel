# Architecture

## Storage responsibilities
| Store | Holds | Never holds |
|---|---|---|
| SQLite `content.db` | surahs, ayahs, translations, dataset provenance, FTS5 indexes | user data |
| SQLite `user.db` | bookmarks, notes, reading history, download records | Quran text |
| MMKV (native) / localStorage (web) | theme, font sizes, reader mode, selected translation, last-read pointer, flags | Quran data, notes, bookmarks, history |
| Filesystem / OPFS | audio, fonts, Mushaf images, downloaded packages | anything small enough for SQLite/MMKV |

## Why two SQLite files
The spec lists Quran and user data under one SQLite database. They are split into two files because their
lifecycles differ: `content.db` is regenerated by CI and replaced when the app ships new content (a plain file
overwrite, validated by `content_meta.content_version`), while `user.db` must survive every update and is only
changed by append-only migrations. A single file would force a risky merge on every content update.
Bookmarks/notes/history reference `(surah_id, ayah_number)`, which is stable under a numbering convention, so no
cross-file foreign keys are needed.

## Content pipeline
`data/*/<id>/{manifest.json, ayahs.json, ...}` -> `validate-*` (schema, numbering, UTF-8, sha256) -> `build-database`
-> `apps/mobile/assets/db/quran.db` + `content-version.json` -> bundled in the APK -> installed on first launch.
Any validation failure aborts the build.

## Search
FTS5 over derived `text_search` columns. Arabic: harakat/tatweel stripped, alef variants unified.
Translations: NFC. The tokenizer is told that Bengali/Arabic combining marks are token characters
(otherwise words split at every vowel sign). Languages with other combining scripts (e.g. Devanagari) need their
marks added to `FTS_TOKENCHARS` and a test before their translations are enabled.
User input is turned into quoted FTS tokens so it can never inject FTS syntax.

## Platform adapters (apps/*)
mobile: `react-native-mmkv`, `expo-sqlite`. web (phase 6): localStorage + SQLite WASM/OPFS behind the same interfaces.

## Audio
`packages/audio` (pure TS, injected `FileStore` / `AudioHttp` / `PlayerPort`) with Expo adapters in `apps/mobile/src/audio`.
Files live in the filesystem area, preferences in MMKV, nothing in SQLite. See [docs/audio](../audio/README.md).

## Knowledge (history, context, sources)
Source-linked claims, passages and edges live in `content.db` (migrations 2 and 3). Model and enforced rules: [KNOWLEDGE.md](KNOWLEDGE.md).

## Known gaps (tracked, not hidden)
Notes UI, Juz/Page/Hizb navigation screens, downloadable translation packs, web app, optional cloud.

Online hadith providers and the data-source decisions: `HADITH.md` and `../data-sources/RECOMMENDATIONS.md`. All online sources, where each is offered, and the candidates rejected: `ONLINE-SOURCES.md`.
